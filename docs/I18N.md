# Languages

English and Russian, across all three codebases. Adding a language means
touching five places, listed at the bottom.

## Five surfaces, three of which iOS resolves without asking the app

This is the part worth understanding before changing anything, because it is why
there is no single catalogue.

| Surface | Strings live in | Language follows |
| --- | --- | --- |
| App screens | `mobile/src/i18n/{en,ru}.ts` | the in-app setting |
| Shortcuts, Siri, permission prompts | `mobile/locales/{en,ru}.json` | the system |
| Widget & Control Center | `mobile/targets/widget/<lang>.lproj/` | the system |
| Siri phrases | `mobile/locales/ios/<lang>.lproj/AppShortcuts.strings` | the system |
| `wol-unlockctl` | `pc-service/src/wol_unlock/i18n.py` | `$LANG` |

Only the first row can honour the in-app override. iOS resolves an intent's
title for the Shortcuts app, a widget's name for the gallery, and a permission
prompt's wording **before the app runs** — often while it is not running at all.
There is no API for an app to tell the system "render my extensions in Russian
today". Settings says as much, in `settings.language.note`.

The three iOS rows are also three *separate bundles*. An `.appex` is its own
bundle, so `Bundle.main` inside the widget is the extension, not the app: a key
defined only in the app's catalogue renders its English `defaultValue` in the
widget. Duplication between `locales/en.json` and `targets/widget/en.lproj` is
therefore deliberate, and a test asserts it stays.

## The app

A catalogue of flat dotted keys, typed so translations cannot drift:

```ts
export const en = { "wake.awake": "{name} is awake." } satisfies Record<string, Message>;
export type Catalog = { [K in keyof typeof en]: (typeof en)[K] extends string ? string : Plural };
export const ru: Catalog = { /* a missing key is a compile error */ };
```

Two entry points, because half this app's strings are produced outside React:

```ts
const t = useT();              // components; re-renders on language change
t("wake.awake", { name });

import { t } from "@/i18n";    // actions, ApiError.friendly
```

**Plurals.** A value may be `{ one, few?, many }` instead of a string; `count`
picks the form. English uses two forms, Russian three (`пакет` / `пакета` /
`пакетов`), by CLDR's rules — see `plural.ts` and its tests.

**Sentences with an element inside them.** Several captions embed a command name
in a monospace `<Text>`. Rather than cut the sentence into two entries and freeze
English word order, the whole sentence is one entry with a `{cmd}` token and
`splitAround()` splits the *translated* string:

```tsx
const [before, after] = splitAround(t("list.empty.body"), "cmd");
<Text>{before}<Text style={shared.mono}>wol-unlockctl pair</Text>{after}</Text>
```

**Server errors** are localized by `code`, never by the message the service
sent. The codes are normative (PROTOCOL.md 4.1) and the messages are not, so
`ApiError.friendly` stays correct against a service running in any language. A
code with no phrasing of its own falls through to the server's message, which is
at least specific.

## The native targets

Keys are explicit and the English wording travels with them, so a missing
catalogue entry degrades to English rather than to a raw key:

```swift
static var title = LocalizedStringResource("intent.wake.title", defaultValue: "Wake PC")
message = String(localized: "intent.status.locked", defaultValue: "\(pc.name) is locked.")
```

Interpolating into `defaultValue` produces a `%@` format, so the `.strings` value
must keep the same specifiers in the same order. A test checks that.

**How the files reach the bundles.** The app target needs no plugin of its own:
`expo.locales` in `app.json` points at `locales/<lang>.json`, and Expo writes
both `InfoPlist.strings` (from the top-level keys) and `Localizable.strings`
(from `ios["Localizable.strings"]`) into `ios/PCUnlock/Supporting/<lang>.lproj/`,
registering both with the Xcode project.

Those keys are stored **pre-quoted** — `"\"intent.wake.title\""` — because Expo
emits `key = "value";` verbatim and an unquoted dotted key is at best relying on
old-style-plist lexing. Quoted is what Xcode's own tooling produces.

The widget needs no plugin either: `@bacons/apple-targets` adds `targets/widget`
as an Xcode file-system-synchronized group, so every file in it — `.lproj`
folders included — is a target member automatically.

Siri phrases are the one exception. Apple resolves them from a file named
`AppShortcuts.strings`, keyed by the English phrase verbatim including the
`${applicationName}` token, and Expo writes only the two file names above. So
`plugins/withAppShortcutsStrings.js` copies them into the same `.lproj`
directories Expo created and registers them the same way. Phrases cannot be
`LocalizedStringResource`s: Siri needs every language's phrasing at once, not
whichever one the device is set to.

## pc-service

A dict per language in `wol_unlock/i18n.py`, `_("key", **params)` to read it,
language from `$WOL_UNLOCK_LANG`, `$LC_ALL`, `$LC_MESSAGES` or `$LANG`:

```console
$ WOL_UNLOCK_LANG=ru wol-unlockctl devices
```

No gettext: a `.mo` is a build artifact to keep in sync and a runtime dependency
on system locale data, for two languages and a few dozen strings.

**`ApiError.message` is deliberately not translated.** Those strings cross the
wire, where the `code` is the normative part and the app renders its own wording
from it. Translating them would change only log lines, while making logs harder
to match against PROTOCOL.md.

## Adding a language

1. `mobile/src/i18n/<lang>.ts` — copy `ru.ts`, translate; `tsc` names anything missed.
2. `mobile/src/i18n/index.ts` — add it to `LOCALES` and `catalogs`.
3. `mobile/src/i18n/plural.ts` — add its plural rule if it is not two-form.
4. `mobile/locales/<lang>.json` and `mobile/locales/ios/<lang>.lproj/AppShortcuts.strings`,
   then `expo.locales` in `app.json`.
5. `mobile/targets/widget/<lang>.lproj/Localizable.strings`.
6. `pc-service/src/wol_unlock/i18n.py` — add the dict and list it in `CATALOGS`.
7. `mobile/src/app/settings.tsx` — add it to `CHOICES`, named in itself.

## What the tests pin

`npx jest src/i18n` and `pytest tests/test_i18n.py`, on both sides:

- every key present in every language, and no extras;
- identical placeholders (`{name}`) and format specifiers (`%@`, `%1$@`) —
  a dropped one crashes Python's `str.format` and renders a hole on iOS;
- every key Swift asks for exists in the catalogue of the bundle that will be
  asked, which is the failure that is otherwise invisible: it compiles, and then
  silently shows English;
- Siri phrases match the phrases declared in `WUAppIntents.swift` exactly;
- Russian plural forms against CLDR's boundaries, including 11–14 and 21.
