# Shortcuts, Siri and Control Center

Four App Intents, in the **app target**:

| Action | Signed | Needs the phone unlocked |
| --- | --- | --- |
| **Wake PC** | no — a magic packet is unauthenticated UDP | no |
| **Get PC status** | yes, both directions | no |
| **Unlock PC session** | yes, both directions | **yes** |
| **Lock PC session** | yes, both directions | no |

Each takes a PC parameter backed by an `AppEntity`, so a shortcut reads
"Wake *Desktop*" and defaults to the only paired PC. Siri phrases are registered
through `AppShortcutsProvider`, so "Wake my PC with PC Unlock" works with no
setup — or "Разбуди мой ПК через PC Unlock" on a Russian device, from
`locales/ios/ru.lproj/AppShortcuts.strings`. Titles and dialogue are localized
too, and follow the **system** language rather than the app's own setting: iOS
resolves them for the Shortcuts app without running the app. See
[I18N.md](I18N.md).

Put them anywhere iOS accepts a shortcut: a Home Screen icon, a Lock Screen
button, a Control Center control, the Action Button, or a Siri phrase.

## Why the app target and not an extension

This is the part that makes them work where widgets do not.

An App Intent in the app target needs **no entitlement, no App Group and no
separate App ID**. iOS launches the app in the background to run it, and it
reads the app's own container. Nothing has to be provisioned, so nothing can be
stripped during signing — which is exactly what happened to the widget (see
[WIDGETS.md](WIDGETS.md)).

Getting Swift into the app target needs a config plugin. Xcode's App Intents
metadata processor runs per target and scans that target's own Swift, so intents
in a CocoaPods static library — which is what an Expo local module compiles to —
are not discovered without an `AppIntentsPackage` re-export.
`mobile/plugins/withAppIntents.js` copies `mobile/native/*.swift` into the
generated project and adds them to the app target's Sources build phase, because
`ios/` is regenerated by every prebuild.

## How they get their data

`src/state/widgetBridge.ts` mirrors the store to
`Documents/wolunlock-state.json` whenever it changes. `native/WUSharedState.swift`
reads it. Same process, same container, no entitlement involved.

The file holds only what is already in AsyncStorage unencrypted: addresses,
public identities, and the last known lock state. The Ed25519 seed stays in the
keychain and is read separately, by alias, in `native/WUDeviceKey.swift`.

## The protocol, again in Swift

`native/WUProtocol.swift` and `native/WUClient.swift` implement the same
normative spec as `pc-service/.../canonical.py` and `mobile/src/crypto/`:
base64url with the same strict decoder, the canonical request and response
strings, Ed25519 through CryptoKit — whose `rawRepresentation` for a signing key
*is* the RFC 8032 seed `@noble/ed25519` produced.

Responses are verified against the pinned server key **before the body is
parsed**. Without that, anything on the LAN could answer on the PC's behalf and,
for `/v1/unlock`, claim a success it never performed.

## Why Unlock asks for Face ID and Lock does not

```swift
static var authenticationPolicy: IntentAuthenticationPolicy = .requiresAuthentication
```

Shortcuts run from the Lock Screen, Control Center and the Action Button, none of
which require the phone to be unlocked. Without that line, an unlock shortcut
parked in Control Center would be a one-tap route into a desktop session for
whoever is holding the phone — the thing the in-app Face ID gate exists to
prevent.

Wake carries no such policy, deliberately. A magic packet is unauthenticated UDP
that anyone already on the LAN can send, and the worst it can do is turn a
computer on.

**Neither does Lock, and that is the whole point of it.** The trade runs the
other way: locking a session cannot let anyone in, and the worst it can do is
cost its owner a password prompt. The moment you actually want it is the moment
you have walked away from an unlocked desk with a phone you have not unlocked —
so requiring authentication would put the gate exactly where it does no good and
the most harm. `LockPCIntent` has no `authenticationPolicy` line for that reason,
and the omission is documented at the point where it is missing.

## Known limits

- **Wake is unicast-first.** UDP broadcast needs the multicast entitlement,
  which requires a paid team *and* Apple's approval. Unicast wake depends on the
  router still holding an ARP entry for the sleeping PC; a DHCP reservation plus
  a static ARP entry makes it reliable.
- **The app must have run at least once** since pairing, so that the state file
  exists.
- **Actions fail with a message rather than silently.** A PC that is asleep, a
  revoked device, or a clock skew all come back as text the shortcut can show.
